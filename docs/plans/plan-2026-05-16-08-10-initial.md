# NarinTown — 게더타운형 가상 오피스 (1784 컨셉) 구현 플랜

> 모든 소스/문서는 `NarinTown/` 하위에 둔다. 공동 작업자가 접근할 수 있도록 플랜·의사결정·Q&A 기록은 `NarinTown/docs/`에 마크다운으로 보관한다.

## Context

게더타운 같은 2D 가상 오피스 앱을 처음부터 만든다. 예상 동시접속 40명, 네이버 1784 사옥 분위기를 차용한 단일 통합 맵. 핵심 차별 요소는 **OX 퀴즈 미션**: 사용자는 입장 시 자기소개 "명함 스킬"과 자신만의 OX 퀴즈 1개를 등록하고, 맵에서 다른 사용자를 만나면 그 사용자의 퀴즈에 도전한다. 상대별 1회 제한, 맞추면 점수 획득 → 전체 리더보드 반영.

WebRTC 음성/영상은 범위에서 제외. 로컬 개발 우선, 추후 Dockerfile 기반 배포로 확장.

처음부터 고도화 구조로 가져가기 위해 **서버 권위적(authoritative) 상태 모델**과 **수평 확장 가능한 Socket.IO + Redis 어댑터** 패턴을 채택. 40명은 단일 노드로 충분하지만, 구조 자체는 노드 추가로 확장 가능하게 둔다.

## 결정된 요구사항 요약

| 항목 | 결정 |
|---|---|
| MVP 기능 | 2D 이동·아바타 / 텍스트 채팅(전체+근접) / OX 퀴즈 미션 / 점수·콤보·랭킹 / 관리자·사용자 대시보드 |
| 스킬 정의 | 자기소개 명함 스타일 (텍스트 태그·전문분야). **게임 능력치 효과 없음** — 이동 속도 부스트, 투명화, 데미지 같은 게임 메커니즘에 영향을 주지 않는 순수 정보 표시 요소 |
| 퀴즈 트리거 | 근접 시 자동 팝업 (양측 동시 트리거 시 서버가 페어 매칭) |
| 재도전 정책 | **상대별 1회** — 같은 상대에게 재도전 불가, 다른 상대에겐 신규 |
| 보상 | 정답 +10, 콤보 보너스, 누적 점수 → 실시간 리더보드 |
| 인증 | 초대 코드 + 이메일 매직링크 |
| 맵 구조 | 단일 통합 맵 (씬 구조로 후에 다층 확장 가능) |
| 아바타 | 레이어 조합 커스터마이즈 또는 기존 IP 캐릭터셋(예: 포켓몬 스프라이트) 활용 — 내부용이므로 IP 사용 OK |
| 에셋 전략 | AI 이미지 생성 또는 1784 실제 사진 활용 → 품질 미흡 시 CC0 픽셀 에셋으로 폴백. 비공개/내부용 전제로 라이선스 자유 |
| 영속화 | 프로필·점수·도전 기록 DB 저장. 재접속 시 **마지막 위치**까지 복원 |
| 첫 입장 배치 | 맵 내 사전 정의된 스폰존에서 **랜덤 배치** (불특정 상대와 만나도록) |
| 이탈 처리 | 이탈 없음. 무입력 5분 시 zZz "잠든 상태" 표시 (반투명). 잠든 상태에서도 퀴즈 응답은 가능 |
| 운영 도구 | 관리자 대시보드 (접속자/초대코드/통계), 사용자 대시보드 (실시간 랭킹·내 기록·현재 콤보) |
| 신고 기능 | **제외** — 40명 지인 그룹용이라 불필요 |
| 온보딩 마무리 | 초가 꽂힌 케이크 + 방금 만든 아바타가 초를 끄는 축하 애니메이션 |
| WebRTC | 제외 |
| 배포 | 로컬 개발 우선, Docker Compose + Multi-stage Dockerfile |

## 기술 스택 (제안)

### Frontend
- **Next.js 15** (App Router) + TypeScript — 인증·프로필·랭킹 등 일반 UI
- **Phaser 3** — 게임 캔버스 (이동·렌더링·충돌). 게더타운류 2D에 가장 적합
- **Tailwind CSS** — 채팅창·프로필 모달 등 UI 레이어
- **Zustand** — 클라이언트 상태 (현재 사용자, 채팅 로그, 근접 사용자 목록)
- **Socket.IO Client** — 실시간 통신

### Backend
- **Node.js 20** + TypeScript
- **Fastify** — HTTP API (인증, 매직링크, 프로필 CRUD, 리더보드 조회)
- **Socket.IO** + **@socket.io/redis-adapter** — 실시간 게임 이벤트, 수평 확장 대비
- **Prisma + PostgreSQL** — 영속 데이터 (User, Profile, Quiz, Attempt, Score)
- **Redis** — 실시간 룸 상태, 위치 캐시, 세션, Pub/Sub
- **Nodemailer** (로컬은 MailHog, 운영은 Resend로 교체 용이) — 매직링크 메일

### Infra
- **pnpm workspace 모노레포** — `apps/web`, `apps/game-server`, `packages/shared` 구조
- **Docker Compose** — 로컬: postgres + redis + mailhog + web + game-server
- **Multi-stage Dockerfile** — apps 각각

### 왜 이 조합인가
- Next.js + Phaser: 인증/대시보드는 React로, 게임 캔버스만 Phaser로 분리해 관심사 명확. Next에 Phaser를 다이내믹 임포트로 끼우는 패턴이 정착돼 있음.
- Fastify + Socket.IO: Express보다 빠르고 스키마 기반 검증이 깔끔. Socket.IO는 자동 재연결·룸·바이너리 등 게임에 필요한 기능 풍부.
- Redis adapter: 처음엔 단일 노드여도 코드 변경 없이 노드 추가 가능.
- Prisma: 스키마 마이그레이션·타입 안전성이 모노레포 공유 타입과 잘 맞음.

### 핵심 설계 원칙
1. **서버 권위**: 클라이언트는 입력(intent)만 보내고 위치는 서버가 결정·브로드캐스트. 치팅/일관성 문제 차단.
2. **Tick 기반 동기화**: 20Hz(50ms)로 위치 스냅샷 브로드캐스트. AOI(시야 반경)에 들어온 사용자만 전송.
3. **이벤트는 권한별 분리**: `player:input`(클라→서버), `state:tick`(서버→클라 브로드캐스트), `quiz:request`/`quiz:answer`/`quiz:resolve` 등.
4. **재접속 복원**: 클라가 토큰으로 재연결 → 서버가 마지막 위치/점수 복원.

## 데이터 모델 (Prisma 스키마 초안)

```prisma
model User {
  id          String   @id @default(cuid())
  email       String   @unique
  nickname    String   @unique
  avatarKey   String   // 미리 정의된 아바타 스프라이트 ID
  createdAt   DateTime @default(now())
  profile     Profile?
  quiz        Quiz?
  attempts    Attempt[] @relation("Challenger")
  receivedAttempts Attempt[] @relation("Target")
  score       Score?
}

model Profile {
  userId      String   @id
  user        User     @relation(fields: [userId], references: [id])
  skills      String[] // 명함 태그 (예: ["React", "Backend", "DevOps"])
  bio         String?  // 한 줄 소개
}

model Quiz {
  userId      String   @id
  user        User     @relation(fields: [userId], references: [id])
  question    String
  answer      Boolean  // O=true, X=false
}

model Attempt {
  id           String   @id @default(cuid())
  challengerId String   // 도전자 (퀴즈 푸는 쪽)
  targetId     String   // 퀴즈 주인
  guess        Boolean? // O=true, X=false, null=기권/타임아웃
  isCorrect    Boolean  // 기권이면 false
  forfeited    Boolean  @default(false) // 기권 여부 (UI 구분용)
  attemptedAt  DateTime @default(now())
  challenger   User     @relation("Challenger", fields: [challengerId], references: [id])
  target       User     @relation("Target", fields: [targetId], references: [id])
  @@unique([challengerId, targetId]) // 상대별 1회 정책 강제
}

model Score {
  userId          String   @id
  user            User     @relation(fields: [userId], references: [id])
  points          Int      @default(0)
  correctCount    Int      @default(0)
  currentStreak   Int      @default(0)  // 현재 연속 정답
  bestStreak      Int      @default(0)
  updatedAt       DateTime @updatedAt
}

model LastPosition {
  userId    String   @id
  user      User     @relation(fields: [userId], references: [id])
  x         Int
  y         Int
  dir       String   @default("down") // up|down|left|right
  updatedAt DateTime @updatedAt
}

model InviteCode {
  code        String   @id
  usedBy      String?  // userId, null이면 미사용
  expiresAt   DateTime?
  createdBy   String?  // 관리자 ID
  createdAt   DateTime @default(now())
}

model MagicLink {
  token       String   @id
  email       String
  expiresAt   DateTime
  consumedAt  DateTime?
}

model AdminUser {
  userId  String @id  // User.id 참조. 관리자 권한 부여
  user    User   @relation(fields: [userId], references: [id])
}
```

`@@unique([challengerId, targetId])`로 **상대별 1회 정책을 DB 레벨에서 강제** — 클라/서버 양쪽에서 실수해도 데이터 무결성 유지.

## 게임 루프 / 실시간 프로토콜

### 입장
1. Next.js에서 매직링크로 인증 → 세션 쿠키 발급
2. `/onboarding`에서 닉네임·아바타·스킬·OX 퀴즈 입력 (없으면 강제 단계)
3. 온보딩 완료 시 케이크 축하 컷씬 (`OnboardingCelebrationScene`) 재생
4. `/play` 진입 → Phaser 씬 로드 + Socket.IO 연결 (`auth: { token }`)
5. 서버: `room:join` 처리
   - **첫 입장**: 스폰존 빈 타일 중 무작위 위치 선택
   - **재접속**: `LastPosition`에서 마지막 좌표 복원
   - 응답으로 본인 시작 위치 + AOI 내 다른 사용자 상태 전송

### Tick 루프 (20Hz)
- 클라: 키 입력 시 `player:input { dir, t }` 전송 (rate-limited, 최대 60Hz)
- 서버: 입력 큐를 50ms마다 처리 → 위치 갱신 → 충돌 검사 → 각 사용자의 AOI(예: 화면 ±400px) 내 다른 사용자 위치를 `state:tick { players: [...] }`로 전송
- 클라: 수신한 다른 사용자 위치를 보간(interpolation)

### 퀴즈 매칭 (근접 자동 팝업)

**페어링 발생 조건**: tick에서 두 사용자 거리 ≤ N 타일 + 양쪽 모두 진행 중 퀴즈 없음

**역할 구분 (서버가 판정)**
- **유발자(Initiator)**: 마지막으로 이동한 쪽. 자발적으로 접근했으므로 무조건 도전 처리
- **대상(Target)**: 가만히 있던 쪽. active면 유발자와 동등하게 처리, sleeping이면 예외 처리

**처리 흐름**
1. 서버: `Attempt` 유니크 제약 확인 (양방향 둘 다, 이미 도전 기록 있으면 매칭 스킵)
2. 양쪽에 `quiz:prompt { partnerId, partnerNickname, question, timeLimit: 15 }` 송신
   - 잠든 사용자에게도 전송 → 입력하면 자동 깨어남
3. **15초 타이머 시작**, 양쪽 응답 또는 타임아웃 대기
4. 타임아웃 시 비대칭 처리:
   | 역할 | 활성 상태 | 미응답 시 |
   |---|---|---|
   | 유발자 | active | **기권 처리**: `Attempt(guess=null, isCorrect=false)` 생성, 점수 0, 콤보 리셋, 기회 소진 |
   | 대상 | active | **기권 처리**: 유발자와 동일 |
   | 대상 | sleeping (입력 없음) | **기회 유지**: `Attempt` 미생성, 다음에 마주치면 재시도 가능 |
5. 응답한 쪽은 `Attempt` 생성 + 점수·콤보 갱신
6. `quiz:resolve { result, score, combo }` 송신
7. 락 해제 후 두 사용자에 5초 쿨다운 (재충돌 방지)

**유발자 판정 로직**: 페어링 발생 직전 tick에서 위치 변화가 있던 쪽이 유발자. 둘 다 움직였다면 거리 변화가 더 큰 쪽 (접근 속도 빠른 쪽). 둘 다 정지 상태(불가능한 케이스지만 안전망)면 둘 다 유발자로 간주.

### 채팅
- 전체: `chat:global { text }` — 모두에게 브로드캐스트, Redis Stream에 최근 200개 보존
- 근접: `chat:proximity { text }` — AOI 내 사용자에게만, 휘발성

## 아바타 시스템

**두 가지 방식을 병행 구현**하고 사용자가 온보딩에서 선택. MVP에서 직접 비교 후 일원화 여부 결정.

### 방식 A: 레이어 조합 커스터마이즈
- `base(체형) + hair + outfit + accessory` 스프라이트를 런타임에 합성
- 각 레이어별 4방향(상/하/좌/우) × 걷기 4프레임 = 한 종류당 16 스프라이트
- 베이스 2종, 헤어 6종, 의상 6종, 액세서리 4종 → 약 288가지 조합
- `avatarKey` 형식: `layered:base=1|hair=3|outfit=2|acc=0`

### 방식 B: 포켓몬 등 기존 IP 캐릭터 선택
- 미리 준비된 포켓몬 BW 스프라이트(또는 동급 픽셀 캐릭터셋) 풀에서 1종 선택
- 구현 단순, 시각적 즉시 인식 가능
- `avatarKey` 형식: `preset:pokemon_025` (피카츄 = 025)

### 공통
- **온보딩 UI**: 탭으로 두 방식 전환 → 양쪽 미리보기 후 선택 → 결정
- **렌더링**: 클라가 `avatarKey` prefix(`layered:` / `preset:`)로 분기 처리
- **저장**: `User.avatarKey` 단일 컬럼에 위 형식 그대로 저장
- 입장 후 프로필 메뉴에서 변경 가능

## 잠든 / 끊김 / 이탈 처리 (캐릭터 영속 정책)

**원칙**: 첫 입장 이후 캐릭터는 맵에서 절대 사라지지 않는다. 로그아웃 액션을 명시적으로 실행한 경우에만 제거.

| 상태 | 트리거 | 시각 표현 | 퀴즈 가능 여부 |
|---|---|---|---|
| `active` | 일반 접속, 입력 있음 | 정상 | O (15초 내 응답 필수) |
| `sleeping` | 5분 무입력 (접속 유지) | 반투명 + zZz | O (응답 안 하면 기회 유지) |
| `disconnected` | 소켓 끊김 (브라우저 닫기/네트워크) | 반투명 + zZz + 회색 톤 (외부 구분 미세) | O (시각적으로 `sleeping`과 거의 동일하게 처리. 페어링 발생 시 응답 불가 → 잠든 상태와 동일하게 기회 유지) |
| `removed` | 사용자가 명시적으로 "퇴장" 액션 실행 | 맵에서 사라짐 | - |

### 세부 규칙
- `disconnected` 상태도 player 목록에서 유지하고 `LastPosition`의 좌표로 계속 표시
- 재접속 시 마지막 위치 그대로 복원 → 자연스럽게 `active` 복귀
- `removed`는 별도의 "퇴장하기" UI 버튼으로만 가능 (MVP에서는 우선순위 낮음, 옵셔널)
- 페어링 매칭 시 `sleeping`/`disconnected` 모두 비대칭 처리 대상 (기회 유지)

### 잠든 상태 동작 디테일
- 클라가 마지막 입력을 보낸 시각을 서버에서 트래킹
- 5분 무입력 → `state.status: sleeping`으로 전환
- 브로드캐스트되는 player 페이로드에 `status` 포함 → 다른 클라가 반투명 + 머리 위 `zZz` 아이콘 렌더
- 사용자가 다시 키 입력하면 즉시 `active`로 복귀
- 잠든 사용자에게 페어 매칭 발생 시: 모달 송신 → 입력으로 자동 깨어남. 미입력 시 기회 유지 (Attempt 미생성)

### 스폰존 정의
- Tiled 맵에 `spawn` 이름의 오브젝트 레이어로 정의
- **로비 입구 근처가 아니라 맵 전체 범위에 분산된 40개 후보 타일** 지정 (오픈오피스/라운지/카페테리아/회의실 입구 등 곳곳)
- 충돌 레이어(벽/가구) 위와 겹치지 않게 검증
- 서버가 빈 스폰 후보 중 무작위 선택. 모두 차 있으면 가장 가까운 빈 타일

- 즉, 실시간 위치는 메모리/Redis, 영속 위치는 DB에 디바운스 저장

## 동시접속 40명 처리 — 서버 부담 분석

### "서버 권위 모델, 40명에 감당 가능한가?" 정량 분석

**Tick 처리 비용 (20Hz, 50ms 주기)**
- 입력 처리: 40명 × 평균 키 입력 60Hz 중 일부 → 최악 40 × 20 = 800 input/s. tick당 입력 큐 비우기는 단순 산술 연산이라 마이크로초 단위
- 위치 산정 + 충돌 검사: 40명에 대해 타일맵 충돌 검사 = O(N), 매 tick 40회 → 50μs 미만 (단순 인덱스 룩업)
- AOI 계산: naive하게 O(N²)=1,600쌍이지만 그리드 공간 분할로 O(N×k)로 축소. 40명 정도면 그냥 O(N²)도 무방
- 브로드캐스트: 40명 × 평균 시야 내 8명 = 320 메시지/tick × 20Hz = **6,400 msg/s**, 페이로드 ~30B → 약 192KB/s. 단일 노드 트래픽으로 매우 가벼움
- **결론**: tick 처리 자체는 단일 노드 CPU의 1~3% 수준. 40명은 매우 여유롭게 감당 가능

**메모리**
- 사용자별 상태: 위치(8B) + 방향(1B) + status(1B) + 메타(~50B) ≈ 100B → 40명 = 4KB. 무시 가능
- 소켓 연결: Node.js 소켓당 ~50KB → 2MB. 무시 가능

**DB 부하**
- 위치는 메모리/Redis만, DB 쓰기는: 매직링크 발급/소비, 프로필 변경, **퀴즈 시도(Attempt)**, **점수/콤보 갱신(Score)**, **위치 디바운스 저장(LastPosition, 5초 단위)**
- 최악 시나리오: 40명 × 5초당 1회 LastPosition 갱신 = 8 writes/s + Attempt 폭주(이론적 최대 분당 수 회) → 합쳐도 PostgreSQL 단일 인스턴스 부담의 1% 미만

**네트워크 (클라당)**
- 수신: 화면 내 8명 위치 × 20Hz × 30B ≈ 5KB/s — 무선 환경에서도 무리 없음
- 송신: 입력 이벤트만, ≈ 1KB/s

### 노드 분할 임계점 (FYI)
- 단일 노드(2 vCPU, 4GB RAM) 기준 **약 500~1,000명까지 단일로 처리 가능** (Node.js Socket.IO 일반적 한계)
- 40명은 임계점 대비 5%도 안 됨. 처음부터 Redis Adapter를 두는 이유는 "성능"이 아니라 **무중단 배포·복제 등 운영적 이점**
- 실제 병목은 클라 GPU 렌더링(40 캐릭터 동시 렌더)이 먼저 올 가능성. Phaser는 50~100 스프라이트는 60fps 무리 없음

### 부하 테스트 시나리오
- 40 가상 클라가 무작위 이동 + 5분간 50회 퀴즈 시도
- 도구: `artillery` + `socket.io-load-tester` 또는 Playwright headless 40개
- 목표: tick 처리 < 10ms (p99), 메시지 지연 < 100ms (p99), 메모리 < 200MB, CPU < 30% (단일 vCPU 기준)
